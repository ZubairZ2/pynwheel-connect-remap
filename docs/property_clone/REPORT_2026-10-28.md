## 1. How it works, in one paragraph

`PropertyClone::Policy` is the dependency map as code: 76 ordered steps (table, how its source rows are found, which foreign keys and polymorphic pairs are remapped, which columns are sanitized, per-row overrides) plus the statuses step, the six serialized columns that embed ids, and 30 exclusion entries with their reasons. `Plan` resolves it against one property without writing (the dry run: counts, predicted skips, files, exclusions, conflicts). `Runner` executes the plan in one transaction under `pg_advisory_xact_lock('property_clone', source id)`: every row is copied with `INSERT ... SELECT ... FROM t WHERE id = ? RETURNING id`, so values keep their exact types and no callback, validation, PaperTrail version, uploader or job fires; self references and the serialized id columns are rewritten in a second pass. `Baseline` fingerprints the source footprint before and after (`md5(string_agg(row::text ORDER BY id))` per table, plus the company, siblings, users, assignments, bookings and global path counts). `Verifier` runs the 13 integrity checks. `FileCopier` copies the property's S3 folders under the clone ids after COMMIT. `TestAdmin` bootstraps the administrator. `Manifest` writes the audit JSON (ids, names, counts, the full source-to-clone id map, exclusions, verification, files, baseline) with no secret or personal data.

## 6. Findings that are not the script's (pre-existing, reported, unchanged)

1. **46 of the 76 legacy HTML controllers do not run `ApplicationController#check_community`** (ToursController, TourStopsController, HallwaysController, WebpagesController, ReportsController, SchedualToursController, the lock-account controllers, ...). Any signed-in CMS user can open or act on those pages for any property by id; the rehearsal proved it with the source's tour page. The Connect JSON paths (`Connect::ReadsJson` / `WritesJson`, `User#can_access_community?` / `can_edit_map?`) are keyed on ids and do refuse. Recommended fix, needing the owner's approval because it changes legacy flow: run `check_community` for every `community_id` route in `ApplicationController`. Until then the test administrator must be a trusted person.
2. **`Ability` has no rule for the `Company admin` role**, so `CompaniesController` (`load_and_authorize_resource`) answers 403 to it, including `GET /companies.json` for its own company.
3. **`TourStopsController#destroy` deletes `Path.where(map_path_from_id: stop_id)` with no type or property filter**: deleting a stop (on any property) can delete another property's legacy routing paths whose `map_path_from_id` happens to equal the stop's record id. Hazel has no paths, so the rehearsal did not exercise it; the baseline carries the global `paths`/`path_points` counts so a future rehearsal would show it.
4. The dry-run of Hazel showed every unit's `floorplan_id` as "would be cleared" in the first version of the policy: `units.floorplan_id` is a string PMS code, not a foreign key (`Unit` resolves it through `floorplans.provider_floorplan_id` within the property). The policy copies it verbatim now; the `tour_stops.unit_id` association in the model has no column either.
5. The first execution reported check 5b FAIL: the value-fidelity digest included the serialized id columns that are rewritten by design (`favorite_stops.favorite_unit`, `hallways.next_points`, `tours.sort_hash`). The verifier now excludes them (they are covered by 8b); `rake property_clone:verify` on the same manifest then reported 13/13 PASS, which is the result in §3.
6. In the test environment the HTML layout does not render (a Sass `rgba` arity error in the asset pipeline), so HTML pages in integration tests can only be checked for redirects.

## 7. Open items, risks and production prerequisites

- **Files**: the S3 phase is untested against a real bucket. Before production, rehearse `property_clone:execute` without `SKIP_FILES` on a staging database whose `S3_BUCKET_NAME` is a staging bucket, and read the manifest's `files.by_status`. Until a folder is `COPIED`, its `*_url` columns read the source objects (read-only); a source re-upload would then change what the clone shows.
- **Idempotency marker**: there is no schema marker; a second run is refused while a `<company> [SCRIPT TESTING]` company exists, and the manifest is the record. A `property_clones` audit table would be more robust; it needs a migration and the owner's approval.
- **Approval needed to copy**: bookings (`schedual_tours`), visit history, visitors, prospects, residents, allowed e-mails, visitor tours. The policy excludes them; a step can be added once the owner decides how PII is handled.
- **Policy decisions taken by default** (change on request): `data_provider` and both credential tables' identifiers are cleared (the clone cannot sync or push to a PMS/CRM); per-stop `lock_provider` stays while access codes, lock accounts and devices do not; `communities.code` is cleared; contact e-mails/phones are cleared; `created_at`/`updated_at` are copied.
- **Legacy gaps** of §6 (1) and (3) stand between the clone and "a test administrator cannot reach the source through the legacy CMS".
- `/companies.json` 403 for the `Company admin` role means the Connect Companies screen is empty for the test administrator; the Properties screen and everything under the property work.
