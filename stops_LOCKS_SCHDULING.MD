## 3. Non-Negotiable Architecture and Database Rules

### 3.1 Reuse the existing system

Before adding new code, follow this investigation order:

```text
Existing UI / feature
        ↓
Existing API and repository
        ↓
Existing Rails controller
        ↓
Existing domain model and relationships
        ↓
Existing service / business logic
        ↓
Identify the genuine missing capability
        ↓
Implement the smallest compatible extension
```

Reuse existing domain models, validations, services, integrations, and state transitions wherever possible.

Do not:

* invent a new business rule when one already exists;
* create duplicate models for existing business entities;
* add duplicate endpoints for existing capabilities;
* independently reproduce backend business logic in React;
* replace working backend functionality with frontend-only calculations;
* change API contracts unnecessarily;
* create mock data to make a feature appear operational when real data is available.

### 3.2 Backend changes are allowed when necessary

Unlike a frontend-only prototype, this task requires functional backend integration for the specified modules.

Make the smallest necessary backend changes when existing APIs or business logic cannot support a required workflow.

Prefer backward-compatible additions. Any required API, model, validation, or service change must be explained and tested.

Do not undertake a general Rails rewrite or unrelated backend cleanup.

### 3.3 Production database restrictions

The live legacy HTML/ERB application and the new Next.js application share the same production database. Protect the legacy application and production data throughout this task.

A production database URL has previously been provided locally or in project context for read-only inspection. Search the available project documentation and local configuration for the established connection mechanism. Never reveal its credentials.

**Production access is strictly read-only for this task.**

Allowed:

* Read-only SQL queries.
* Inspecting company and property relationships.
* Checking existing Stops, Locks, Visitors, bookings, provider configurations, and scheduling data.
* Reading production records to understand real-world configurations.
* Comparing existing production data with a safe local or staging environment.

Not allowed:

* Production database writes.
* Production migrations or schema changes.
* Production seeding or test-data creation.
* Running state-changing Auto Detect, mapping, import, deletion, publish, or booking operations against production.
* Changing production lock mappings, access codes, integrations, bookings, or Tour Stops for testing.
* Modifying the running legacy production application as part of this task.

Use a local or isolated staging database for all required creation, update, mapping, scheduling, booking, import, and deletion tests.

If production data is needed to reproduce a case, copy only the necessary records into an authorized local/staging test dataset, respecting data-handling requirements and preserving the relevant relationships.

**The shared production database must remain untouched by write operations, and the existing legacy application must remain operational.**
