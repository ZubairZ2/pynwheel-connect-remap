**Date:** October 10, 2026 · **Branch:** `fix/svg_dual_map_asset_delivery_and_hallway_detection` (from `main` `2fe6f7d66`, which includes the upstream merge of October 10) · **Brief:** `cypress_company_issue.md`

## 7. Auto-Detect validation

Geometry inspected: the nine real exports listed in §2–4 (downloaded from the production bucket into a scratch folder — not committed — and read into `tests/e2e/hallways.spec.ts` through `PYN_CONNECT_REAL_SVG_FIXTURES` when present; `svg_map_qa/scripts/svg_structure.py` / `svg_layers.py` print what was read). Engine changes (`detectLayers.ts`, `extract.ts`):
1. **Shared background** — `detectSvgStructure(root, background)` reads the property's background file beside the floor file; its walkways, footprints and obstacles fill in what the floor file lacks, mapped into the floor's frame through the two viewBoxes (`viewBoxMap`; the Beans exports share one viewBox exactly).
2. **Building outlines as footprints** — with no `Footprints` layer, `Building_outline` / `Building Outlines` / `Outline …` (closed, filled) are the footprints corridor inference reads, and remain obstacles for synthesised links.
3. **Traced + inferred, joined** — beside *generically named* walkway art (`Path`), corridors are inferred inside the footprints between the rooms and the two graphs are bridged at the doorways; a labelled `Walkways` / `Sidewalk` / `Corridor` / `Hallway` layer is the designer's word and is traced alone (the POC's behaviour and its parity numbers are unchanged; `inferBesideWalkways` option).
4. **Diagnostics** — a file with no named layers at all is `no-layers` (told apart from `no-hallway-layer`); every detected row says where the paths came from and how many of the floor's stops they joined; a graph that joins nothing is said to.
Repeatability: a second run on a detected floorplate keeps the result ("Existing paths kept"); Undo takes a run back; nothing stored is replaced (unchanged rules). No persistence was exercised against production; Save was not pressed on the clone.

## 8. Asset delivery

`Connect::UploadUrl` (Rails, used by `floorplates.json`, every inventory serializer and the Tour App API's level SVGs): a stored key is now looked for on the configured bucket, then the record's family bucket, then the property's, then on **every bucket the database's recent raster uploads name** (`known_buckets`, cached a day); the first copy that answers 2xx wins, a check that could not be made no longer keeps a wrong URL, and nothing is probed when the database names no other bucket (production: zero HEADs, as before). The `plan-svg` route's 45 s limit now covers the body stream too (a store that answers at once but streams a few MB over minutes — seen from this machine — is reported as `timeout` and can be retried), and the route reports the failure class (`upstream` with S3's status, `timeout`, `network`, `not-svg`, `missing`, `unauthorized`, `listing`), the stored file name and the answering host — never a URL or a signed query — and sniffs that the body is an SVG document. The canvas prints that reason under the message; Retry issues a fresh request (the CMS re-resolves the URL) and shows the loading state.

**Verified:** on the clone with floorplate 4604's stored name deliberately broken, Floor 3 showed "The file store answered 403 for bogus-1790021794-Floor_3_noBG.svg (images-pynwheel-cms-v2.s3-accelerate.amazonaws.com)" with the route answering `502 {"ok":false,"error":"upstream","status":403,…}`; see the matrix for the Retry rounds. Direct probe of the production bucket: §2.

## 11. Database safety

- Production was read through the read-only credential in `~/.pynwheel_ro_url` (`current_user = readonly-debug`, `default_transaction_read_only = on`, a 30–60 s statement timeout, every query in `svg_map_qa/sql/q1–q4.sql`, run by `svg_map_qa/scripts/prodq.sh`); the connection string was never printed (the runner redacts any `postgres://` text). - Every write-shaped test (Detect, Clear Paths, the broken-row Retry test, the Cypress Terra unit sync, the two upstream migrations) ran on the local clone `pynwheel_audit_clone`; the broken row was restored (`1790021794-Floor_3_noBG.svg`). Nothing was saved to any CMS from the page (0 non-GET requests in every run).
- **Noted risk:** Heroku `pyn-system` (the CMS behind `pyn-system-connect`) has `DATABASE_URL = PYNWHEEL_PROD_DATABASE_URL`, the production database itself, while `S3_BUCKET_NAME=staging-pynwheel`. Connect writes there are gated (`PYN_CONNECT_WRITES=off`, v18), but any upload from that CMS would land on the staging bucket while its rows live in production.

## 11a. A regression found by the regression run, and fixed

The first run of the standing real-data map specs against the development-database pair (`svg_map_qa/logs/regression-dev.log`: 16 passed, 15 failed in 39.5 min, every failure a page-load or wait timeout) was traced to the first version of the resolver: under development's file storage it had started sending HEAD checks for every upload whose file is not on disk, each timing out after 3 s from this machine's slow link to S3 and never being cached, so Hazel's amenity galleries alone pinned Puma's five threads for minutes and starved every other request (a Sylo floor SVG took 438 s to come through). The resolver now probes only under fog storage (where S3 answers in milliseconds) and remembers a failed check for five minutes; file storage names the bucket the database points at without a request, as it did before. The second run (`svg_map_qa/logs/regression-dev-second-run.log`) took 8.6 min: 21 passed, 10 failed, and those ten fell into four groups:

1. **Merge fallout on `main`, not this branch:** Connect's Property Detail JSON (`communities/:id/edit.json`) answered 500 with `uninitialized constant Community::MAP_PARTNERS` — upstream's "Make the partner registry data-driven" commit (`0e3dfa5bb`, merged on October 10) replaced that constant with the `Partner` table, and `Connect::PropertyDetailSerializer#partners` still named it. Repaired here in that one method (`Partner.registry`, same keys / labels / enabled flags); the Hazel Property Detail and Navigation tests are its victims.
2. **The specs encoded the old "open on the SVG" default:** three tests on property 1468 (a floorplate with both files, 20 stored hallways and 124 units on the image) expected the floor SVG to mount on arrival; since this change the floorplate opens on its image, where its stored plotting is. The tests now pick "Floor SVG" from the layer switch first, and `mapPlotting`'s toolbar assertion accepts the switch's two buttons.
3. **Stale expectation in the dump, unrelated to this work:** Hazel's "Boardroom · In Stops List" — the amenity's only tour stop (7652) belongs to a visitor's tour (1601), not the property's main tour (1089), so `in_stops_list` is false by its definition; the pill says "Hidden from Stops" correctly. Left as it is and reported.
4. **Bandwidth:** Sylo's floor SVGs are 4.9 MB each and stream at about 60 s apiece from this machine today (280 KB/s through S3 acceleration); with two workers the 120 s waits of three Sylo / 2919 tests expire. Re-run alone with one worker: see §9.
